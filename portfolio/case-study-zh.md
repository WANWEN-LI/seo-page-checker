# 案例：页面 SEO 与转化体检工具

**李婉雯 · 2026 年 10 月 · [代码](https://github.com/WANWEN-LI/seo-page-checker) · [演示与报告](https://liwanwen.com/seo-checker/)**

## 1. 问题

我做了 5 年亚马逊电商（2 年在公司任职，3 年自己开店），很清楚一条 Listing 的成败取决于细节：标题有没有说清楚卖的是什么、卖点是否一目了然、价格看不看得到、有没有评价、下一步该点哪里。任何需要被搜到、并且要促成转化的页面都是这样，我自己的作品集也不例外。

免费的检测工具通常只给一个分数，不说明分数是怎么算的；SEO 建议里常常混着不相关的内容；而且没法告诉你，按建议改完之后到底有没有变好。我想要的工具应该做到：

- 检查对 Listing、落地页、作品集页真正重要的项目；
- 分数背后的计算规则全部公开；
- 每个问题都写清楚：发现了什么、为什么重要、怎么改；
- 改完之后重新检查，用实测数据显示变化了什么。

## 2. 我做了什么

一个 Python 工具，带 Streamlit 界面和命令行：

- **抓取**：用 `requests` 和 BeautifulSoup。抓取前先读 robots.txt；对同一个网站，每次请求至少间隔 1 秒；只读取公开页面。
- **速度**：调用 Google PageSpeed Insights API，测手机端的 Lighthouse 分数和 Core Web Vitals。
- **打分**：分技术、性能、内容转化三大类，算出 0–100 的总分。每项检查的权重是 3、2 或 1，全部写在 README 里。
- **报告**：生成可以直接分享的 HTML 报告，同时保留原始 JSON 数据。每次检查都会存档，同一个页面的两次结果可以逐项对比。
- **AI 建议（可选）**：用 Claude 改写 title 和 meta description，并给修改建议排序。每条建议都必须对应一项没通过的检查。这部分用模拟的客户端做了单元测试，但在这个项目里还没有真正调用过 API。
- **测试**：59 个单元测试。

## 3. 检查什么、为什么

| 类别 | 检查项 | 为什么重要 |
|---|---|---|
| 技术 SEO | title 长度和关键词、meta description、是否只有一个 H1、标题层级、图片 alt、canonical、robots meta、`lang`、OG 和 Twitter 分享标签、JSON-LD、坏链接、robots.txt、sitemap | 搜索引擎和链接预览最先读的就是这些 |
| 手机端速度 | Lighthouse 性能、无障碍、SEO 三项分数；LCP、CLS、INP（标明是实验室数据还是真实用户数据） | 手机页面太慢，访客还没看到内容就走了 |
| 内容与转化 | 开头是否讲清卖点、有没有行动按钮、关键词有没有出现在 title / H1 / 首段、可读性、按页面类型检查信任元素（产品页看价格、评价、配送；作品集看联系方式和作品） | 把 Listing 优化的思路用到任何页面上 |

## 4. 在 liwanwen.com 上的真实前后对比

**修改前**（2026 年 10 月 18 日，线上网站）：About 页 81 分，最大的问题是手机端速度。Lighthouse 性能分只有 63，LCP 长达 14.0 秒；PageSpeed 的网络记录显示，页面上最大的文件是一张 2.3 MB 的 PNG 头像。4 个页面都缺少 canonical、OG 和 Twitter 分享标签、结构化数据，网站也没有 robots.txt 和 sitemap；另外有 3 个页面的 title 不到 30 个字符。

**做了哪些修改**（都是工具给出的建议，我确认后当天上线）：
- 头像转成 700px 的 WebP（2.3 MB → 57 KB），并设为优先加载；
- 首页的视频改成滚动到屏幕里才加载；
- 加上 canonical、robots.txt、sitemap、Person 结构化数据和分享标签；
- 每个页面都换上不重复的 title 和 meta description；
- 网页字体不再通过 CSS 里的 `@import` 加载，避免阻塞页面渲染。

**修改后**（在线上网站重新检查）。速度相关的几列，是多次独立 Lighthouse 手机测试的中位数：

| 页面 | 工具总分 | Lighthouse 性能 | LCP | 测试次数（前 → 后） |
|---|---|---|---|---|
| /about | 81 → 93 | 63 → 92 | 14.0 s → 2.4 s | 4 → 3 |
| / 首页 | 85 → 93 | 75 → 75.5 | 4.8 s → 4.8 s | 3 → 4 |
| /projects | 84 → 92 | 82 → 83 | 3.8 s → 3.8 s | 2 → 3 |
| /photography | 85 → 89 | 87 → 83 | 3.5 s → 4.0 s | 2 → 4 |

这些数字能说明什么，不能说明什么：
- **About 页**：改善明显且稳定，修改后每一次测试都在 91–94 分之间。
- **首页**：两个循环视频（2.0 MB 和 1.7 MB）已经不在 PageSpeed 首次加载的网络记录里了，但 Lighthouse 分数没有可测出的变化。修改后的几次测试在 73 到 92 分之间波动。
- **Photography 页**：速度略有下降。修改后的第一次测试 LCP 是 9.9 秒，那是刚部署完测的，属于异常值；之后几次都在 3.4–4.1 秒之间。具体原因还没查清。
- 4 个页面一共有 27 项检查从"没通过"变成"通过"。工具报告的唯一一处退步，就是 Photography 页那次 9.9 秒的测量。
- 以上都是实验室测量。Search Console 还没接入，所以我不对排名或流量做任何结论。

## 5. 测试中发现的问题（都已修进工具）
- **返回 200 不一定是真页面**：第一个试的电商页面，HTTP 状态是 200，内容却是一个写着 "Hang tight" 的排队页，工具照样给它打了分。现在工具能识别这类反爬虫页和排队页，识别出来就不打分。
- **语言会影响判断**：IKEA 意大利站的页面上写着 "Servizi di consegna"（配送服务）和 "Cambi e resi"（换货与退货），工具却判断成"没有配送信息"。现在工具能识别 6 种语言的信任词，非英语页面也不再套用英文的可读性公式。
- **隐藏文字被算了进去**：HTML 注释被当成了页面上看得到的文字，现在已经排除。
- **Lighthouse 要多测几次**：每次测出来的分数都有波动，而且短时间内重复请求时，PageSpeed 会直接返回缓存的结果。所以我只统计测量时间（fetchTime）不同的结果。

## 6. 限制
- 只读服务器返回的 HTML，不执行 JavaScript；一次只检查一个页面；"首屏"是按前 1,500 个字符估算的。
- CTA、价格、评价的识别靠关键词匹配。比如 IKEA 页面上的图片放大按钮，就被误算成了行动按钮。
- 适合在本地运行，没有针对公开部署做安全加固。
- 不包括关键词搜索量、外链、排名，这些需要付费数据。
